## 0. 现状（代码已核对）

`domain/evaluation/h1.py` 中，H1 的结果有四种：OK、VIOLATION、NOT\_JUDGED、UNKNOWN。

- **NOT\_JUDGED**：主口径事件，F\_ref 在 [p, 报告谷底) 内不存在。这是**已知的"不适用"**：旧规则在这段下跌中不会报警，H1 不约束它，由未提醒率门槛 m 约束。它不是未知，不属甲，也不属乙。
- **UNKNOWN**：
  - 原因来自事件本身：截尾、不可评估、依赖未决，以及前缀完整的右端截尾事件在 [p, k\*) 内找不到 F\_ref；
  - 计算只用价格、公共掩码与本事件的峰值（`find_f_ref` 不接收方法），所以**对所有方法相同**。
- 方法当日的状态由 `method.in_alert(i)` 判断，状态为空即判为不在警，计为违反。现行代码中没有"方法状态未知"这一结果。

## 1. 分类规则

### 1.0 先判定，后分类（RL-01）

对每个事件集中的每个事件，按以下顺序处理，取第一个适用的步骤：

1. **能按现行规则判定的，照常判定**：主口径事件，或前缀完整的右端截尾事件，其 F\_ref 在搜索范围内已确定（17 号第 4 节第一条）。
   - 方法状态完整（第 1.2 节）：OK 或 VIOLATION；
   - 方法状态不完整：乙类，计为违反。
   - **退市截尾的事件只要满足这一步，就照常判定，不进入甲类。**
2. **已知不适用**：主口径事件，F\_ref 在 [p, 报告谷底) 内不存在（NOT\_JUDGED）。不是未知，不计入应检单位。
3. **其余的 UNKNOWN 事件**，按**合并后的原因集合**分类（G-RL-02）：原因集合 = 事件的排除原因（截尾、`UNEVALUABLE_*`、`DEPENDENCY_PENDING`，即 `outcomes.exclusion_reasons(event)`）∪ F\_ref 计算返回的原因（如 `F_REF_ABSENT`）。不得只用 `H1Result.reasons`。
   - 原因集合非空，并且**每个**代码都满足第 1.1 节表中该代码的条件（包括附加代码与依赖未决的条件）：甲类，按各原因类别计数；
   - 原因集合为空，或只要有一个代码不满足（即使同时有满足的代码）：乙类，原因 `UNRECOGNIZED_REASON`，并报告该代码。表中只列明确的代码字符串，今后新增的 `RIGHT_…` 等代码不会自动视为已识别。

### 1.1 甲类：检查点因价格数据本身无法建立

**定义**：经第 1.0 节第 1、2 步之后仍为 UNKNOWN，并且全部原因代码都在下表中的事件。它们的检查点（F\_ref 及其判定日）由于价格数据或数据终点而无法建立；判定只依赖价格、公共可评估掩码与事件状态机，**与方法无关**。

| 原因类别 | 事件上的原因代码（现行实现） | 说明 |
| --- | --- | --- |
| **退市** | `RIGHT_DELISTED` | 退市使事件在确认之前截止，**并且**按第 1.0 节第 1 步无法判定（例如前缀不完整，或 F\_ref 不在 [p, k\*) 内） |
| **缺价** | `MISSING`、`DATA_BREAK`（截尾）；`UNEVALUABLE_MISSING`（不可评估） | 缺价截尾、历史断点，以及 [p, 报告谷底] 内有缺价日（断段中的日子没有日线，也记为缺价） |
| **预热** | `UNEVALUABLE_WARMUP` | 新上市或断点后的新历史段，不满 W + max(N) 个有效日。现行掩码只有缺价与预热两种来源（`series.py`），所以当前标记成立；今后的规则见第 4 节第 1 项（RL-03） |
| **右截尾** | `RIGHT_DATA_END`、`RIGHT_REQUIRED_END`、`RIGHT_PERIOD_END` | 数据终点、必需区间终点、期间终点 |
| **依赖未决**（条件见下） | `DEPENDENCY_PENDING` | 事件附带非空的依赖未决区间。**条件**：依赖对象与截止原因按下面"依赖未决"一段核实；核实不了的不满足条件，按第 1.0 节归乙 |
| （附加代码） | `F_REF_ABSENT` | **只在与某个 `RIGHT_*` 代码同时出现时**才是已识别代码，此时原因类别随那个 `RIGHT_*`：`RIGHT_DELISTED` 归退市，其余归右截尾。单独出现（没有任何 `RIGHT_*`）视为未识别，归乙 |

**依赖未决**（`DEPENDENCY_PENDING`）：
- **依赖对象**：同一证券、同一历史段内，数据终止时仍在待确认的前一个事件。按 17 号第 2.2 节，(e, 数据终点] 内不建立后继事件。
- **为什么归甲**：这个前一事件能否确认，只由价格、公共掩码与事件状态机决定，与方法无关。
- **原因类别**：随该前一事件的截止原因。数据终点、必需区间终点、期间终点归"右截尾"，退市归"退市"。
- **两个检查位置**（G-RL-01）：待确认事件本身，与它的非空依赖未决区间，是两个独立的检查位置：
  - 事件本身：在 [p, k\*) 内检查它自己的 H1，按第 1.0 节判定或分类，计一个事件单位；
  - 依赖未决区间：(e, 数据终点] 内可能存在、但因前一事件未确认而没有建立的后继下跌，计一个区间单位。
  这是有意的"本事件 + 潜在后继区间"两个单位，不是重复计数。
- **计数单位**：这个区间里没有建立任何事件，没有可以逐件列出的事件，所以每个**非空**的依赖未决区间**计为一个甲类单位**，另报它的有效日数与证券日数。这是登记的计数约定，不是对区间中实际漏了几次大跌的估计；报告中事件单位与区间单位分开列出，比例称为"混合检查单位比例"。
- **空区间不计**（RL-02）：区间为 (e, 数据终点]。当 e 等于数据终点时，区间为空：不产生应检单位，也不计甲类。是否为空按区间的边界判断，不按 `valid_days` 判断。非空但区间内全是缺价日的，仍计一个甲类单位，原因类别同上。
- **有疑义的**：依赖对象不是上述前一事件；或者截止原因无法确定。这两种情形都归乙。

**一个事件有多个原因时**：在甲类总数中计一次；各原因类别分别计数，可以重叠。这与 17 号第 2.2 节"不可评估的原因"的计数方式相同。

### 1.2 乙类：检查点存在，方法的状态无法确定，以及其他一切未知

- F\_ref 已经确定，但方法在 F\_ref 当日的日末状态无法确定。
- **方法状态的完整性**（RL-05）：
  - 先核验方法的逐日输出与预期的评价日历**完全对应**：同样的日期、同样的顺序、没有缺日。现行 `method_series.from_run_result` 对引擎方法已做此检查，不对应即报错；B1–B3 等其他方法的适配器必须做同样的检查。
  - 只有输出完整时，`levels[i]` 为空才表示"不在警"。
  - 缺日、日期错位、未运行、运行失败：另存完整性状态，不得用"不在警"填补，相应 H1 检查记乙类，原因 `METHOD_STATE_UNKNOWN`。
- 原因代码不在第 1.1 节表中的任何未知。
- 依赖未决中有疑义的情形（见第 1.1 节）。
- 任何对归类有疑义的情形。

**处理**：乙类一律计为违反，即该方法未通过 H1。报告中与真正的违反分开列出（原因 `METHOD_STATE_UNKNOWN` 等），但计数合并。

### 1.3 预期单位清单与跨方法一致（RL-04）

- **预期单位清单**：对每个证券、每个事件集，独立于任何方法生成：
  - 事件单位：事件链中的全部事件（含截尾与不可评估的），以事件身份标识；
  - 区间单位：全部非空的依赖未决区间，以（证券、依赖事件身份、区间边界）标识。
- **归属**（G-RL-01）：
  - **期间**（入选期间、开发期、验证期）：事件单位按 17 号第 1.2 节，以峰值日 p 归属；区间单位以它依赖的前一事件的峰值日 p 归属。不按可确定日期归属，否则右端截尾事件与未决区间都会因可确定日为空而从期间分母中消失。
  - **两段检查**（前段、后段）：沿用已审定的规则，按指标的可确定日期归属，可确定日为空的记 NEITHER（17 号第 2.2 节、`membership.py`）。右端截尾事件与依赖未决区间因此都记 NEITHER。两段检查只报告，不设门，所以不影响任何判定。
- **检查**：
  - 每个方法的 H1 结果必须覆盖预期清单中的全部单位，不漏、不重；
  - 全部方法的甲类单位集合必须逐件相同，包括候选、B1、B2、B3、R0。比较的内容是单位身份加原因类别。B3 没有 RELEASE，但 H1 只看在警，所以也计入；
  - 预期清单为空时，测试要明确断言"为空"，不能因为"空集等于空集"而视为通过。
- 以测试断言；运行中不同即停止，按工程错误处理（17 号第 5.4 节）。
- B3 没有 RELEASE，但 H1 只看在警，所以 B3 也计入这条比较。

## 2. 甲类的上限与敏感性报告

1. **应检单位**：对每个事件集（E\_pct、E\_atr、E\_pct10）、每个期间，H1 应检单位包括：
   - F\_ref 已确定的事件，即判为 OK 或 VIOLATION 的，以及乙类；
   - 甲类事件；
   - 依赖未决区间。

   **不含** NOT\_JUDGED（F\_ref 已知不存在），但报告中同时列出它的数量。
2. **四个比例**（RLR-02），按每个事件集、每个期间分别计算：

   | 比例 | 分子 | 分母 |
   | --- | --- | --- |
   | ① 事件级甲类比例 | 甲类事件单位数 | 应检事件单位数 |
   | ② 混合甲类比例 | 全部甲类单位数（事件 + 区间） | 全部应检单位数（事件 + 区间） |
   | ③ 事件级退市比例 | 原因类别含退市的甲类事件单位数 | 应检事件单位数 |
   | ④ 混合退市比例 | 原因类别含退市的全部甲类单位数（事件 + 区间） | 全部应检单位数 |

   - 另报各原因类别的单位数，事件单位与区间单位分开列。
   - **零分母**：每个比例的分母为 0 时，该比例记"不可判定"，不填 0，不称上限通过（RL-04）。
   - **两种口径的关系**：区间单位都是甲类，加入后②不低于①；会被稀释的是退市比例（非退市的区间单位进入④的分母）。所以只看混合口径，会低估退市比例。
   - **强制判定的范围**：三个事件集，各自在开发期与验证期分别判定。两段检查的前段、后段只报告，不另设门。这是产品经理拟议，与上限一起在登记时由发起人批准；范围写明后，不在看结果后拆分或合并。
3. **上限**：
   - 甲类上限 U\_甲、退市单项上限 U\_退市。两者都在 T08c 登记（SR-M1′）时由发起人批准。拟定值由产品经理依据探索集的分布写出，附理由。
   - **拟议的判定方式（待批准）**：① 与 ② 各自不得超过 U\_甲；③ 与 ④ 各自不得超过 U\_退市。
   - 上限批准之前，探索阶段只展示四个比例，不生成"通过 / 未通过"结论。
4. **超过上限时**：强制判定范围内任一比例超过对应上限（按批准的判定方式）：
   - 该期间的评价记为"证据不足"；
   - 开发期即没有合格候选，验证期即"无法判定"；
   - 都不得称为通过。
5. **查看限制**：
   - 发起人批准 U\_甲、U\_退市之前，不得计算或查看选参集与验证集的甲类比例。
   - 探索集的甲类比例可以查看，用于拟定上限。
6. **敏感性报告**：
   - 把全部甲类单位按"违反"计，报告每个方法的 H1 违反数；
   - 只作描述，不改变资格、排序或验证结论。
