## 1. 全语义摘要（F-07、I-18）

**问题**：`application/replay_run_types.py` 的 `discrete_digest` 只覆盖日期、显示状态、等级、预警编号、周期与事件键。ATR、计数、事件依据等字段改变时，摘要不变，所以它不能证明"输出完全相同"。

**新增** `domain/lifecycle/semantic_digest.py`，纯函数，不做 I/O：

1. `canonical(obj) -> str`：规范序列化。
   - 输出是紧凑 JSON：`separators=(",", ":")`，`ensure_ascii=False`。
   - **判定顺序**（M-03），按下表从上到下，取第一个匹配的行：

     | 顺序 | 类型 | 编码 |
     | --- | --- | --- |
     | 1 | `datetime` | **拒绝**：抛出异常。它是 `date` 的子类，所以必须先判断。生命周期输出中不应有时间戳 |
     | 2 | `None` | `null` |
     | 3 | 枚举（`Enum` 的子类，含 `IntEnum`、`StrEnum`） | `{"enum":"<模块>.<限定名>.<成员名>"}`。必须先于 `int`、`str` 判断 |
     | 4 | `bool` | `true` / `false`。必须先于 `int` 判断 |
     | 5 | `int` | `{"i":"<十进制>"}` |
     | 6 | `float` | 有限值编码为 `{"f":"<float.hex(x)>"}`，`-0.0` 与 `0.0` 不同。**非有限值（NaN、正负无穷）拒绝**（M-04） |
     | 7 | `Decimal` | 有限值编码为 `{"d":"<str(x)>"}`，保留尾随零（量化位数属于语义）。**非有限值拒绝** |
     | 8 | `str` | JSON 字符串 |
     | 9 | `date` | `{"date":"<ISO 8601>"}` |
     | 10 | 数据类（dataclass 实例） | `{"dc":"<模块>.<限定名>","fields":[[字段名, 值],…]}`，按声明顺序列出全部字段 |
     | 11 | `tuple` | `{"tuple":[…]}`，保持顺序 |
     | 12 | `list` | `{"list":[…]}`，保持顺序。与 `tuple` 的编码不同（G-M0b-03） |
     | 13 | `frozenset` | `{"frozenset":[…]}`，元素先各自编码，再按编码后的字符串排序 |
     | 14 | `set` | `{"set":[…]}`，排序规则同上。与 `frozenset` 的编码不同 |
     | 15 | `dict`（只限 `dict` 本身，不含其他映射类型） | `{"map":[[k,v],…]}`，键与值各自编码，按键编码后的字符串排序。没有出现的键与值为 `None` 的键是两回事。其他映射类型（如 `MappingProxyType`）按第 16 行拒绝 |
     | 16 | 其他任何类型 | **拒绝**：抛出异常，不得用 `str()` 或 `repr()` 兜底 |

   - 拒绝时，异常信息要写出该值在对象中的**字段路径**，例如 `results[12].record.atr_ep`。
   - 如果在真实回放的输出中遇到被拒绝的值（非有限数、时间戳、未列出的类型），停止并报告，不得放宽规则。项目的数值契约要求有限数（`domain/numeric.py`、`lifecycle/params.py` 已做检查）。

2. `semantic_digest(result: RunResult) -> str`：
   - 对 `RunResult` 中的全部内容取摘要：`results` 中每一步的 `state`、`events`（含 `basis`）与 `record`，以及 `final_state`、`censored_episode`。
   - 以版本标识 `"semantic-digest/1\n"` 开头，后接 `canonical(result)` 的 UTF-8 字节，取 SHA-256，输出十六进制小写。

3. **保留** `discrete_digest`，不改，供与历史结果比较。

**测试**（期望全部来自本节的编码规则，不用实现的输出倒填）：

1. **编码单元测试**，手写期望字符串：
   - `canonical(None)` = `null`；`canonical(True)` = `true`；`canonical(1)` = `{"i":"1"}`；
   - `canonical(0.1)` = `{"f":"0x1.999999999999ap-4"}`，这是 IEEE 754 双精度 0.1 的十六进制表示；`canonical(-0.0)` ≠ `canonical(0.0)`；
   - `canonical(Decimal("1.50"))` = `{"d":"1.50"}`，与 `Decimal("1.5")` 的编码不同；
   - `canonical(date(2019, 12, 31))` = `{"date":"2019-12-31"}`；
   - `canonical(Level.WATCH)` ≠ `canonical(1)`；`canonical(Display.NORMAL)` ≠ `canonical("正常")`；两者的编码都含模块与限定名；
   - `canonical(frozenset({"b","a"}))` 与 `canonical(frozenset({"a","b"}))` 相同；
   - `canonical({"x": None})` ≠ `canonical({})`；
   - `canonical((1,))` ≠ `canonical(1)`；`canonical([1])` ≠ `canonical((1,))`；`canonical(frozenset({1}))` ≠ `canonical({1})`；`canonical(1)`、`canonical(1.0)`、`canonical(True)` 两两不同；
   - 以下都抛出异常，并且异常信息中有字段路径：`datetime`、`float("nan")`、`float("inf")`、`float("-inf")`、`Decimal("NaN")`、`Decimal("Infinity")`、一个未列出的类型（例如 `object()`）、一个 `MappingProxyType`。
2. **敏感性**（I-18）：取一个现有生命周期夹具的运行结果作为基准，分别只改下列一项，摘要都必须改变：
   - 某一日 `record.rc`；
   - 某一日 `record.atr_ep`，只改最后一位：用 `math.nextafter`；
   - 某个事件 `basis` 中的一个值；
   - `final_state` 的一个字段；
   - `censored_episode`。

   改动时用 `dataclasses.replace` 构造新对象，不改原对象。同样的五种改动下，断言 `discrete_digest` 都不变（它不含这些字段）。这证明旧摘要确有缺口，新摘要补上了。
3. **顺序无关**：集合字段以不同的构造顺序得到相同内容时，摘要相同。
4. **元数据无关**：见第 5 节第 2 项。

## 2. 模式等价（I-02）

把现有 I17 ② 的检查（`replay_run._i17_check`、`compare/service._i17`）从离散摘要扩展到全语义摘要。

1. **检查范围（M-07）**：本卡**沿用现有的固定抽样**，不扩大到全集。
   - 回放：`I17_SYMBOLS` × `I17_CANDIDATES`，即 5 个对象 × 3 个候选，共 15 个检查键（对象，候选）。
   - 对照回放：`I17_SETS` × `I17_TARGETS`，共 3 套 × 5 个对象，15 个检查键（套，对象）。
   - **预期检查键**：在运行开始时由这两组常量生成。实际检查过的键必须与预期**完全相等**：
     - 缺少任何一个、出现重复、或者检查为空，`i17_ok` 都为假；
     - 现有 `compare/service._i17` 中"`set_id` 不在结果中就跳过"的写法，改为记一个缺项；
     - `manifest` 新增 `i17_expected_keys` 与 `i17_missing_keys`。
2. **比较的模式**（G-M0b-01）：正式运行与专用测试分开。
   - **正式运行内嵌的检查**：保持现有的模式，不增加进程池的重跑次数，避免运行时间翻倍。
     - 回放：单进程不缓存、单进程缓存、多进程缓存三种；
     - 对照回放：单进程不缓存、多进程缓存两种（现状如此，本卡不补单进程缓存）。
     - 改动只有一处：在离散摘要之外，再比较全语义摘要。多进程的工作进程除离散摘要外，还要返回检查键的全语义摘要。
   - **专用测试**：用合成数据，覆盖四种模式：单进程不缓存、单进程缓存、多进程缓存，以及**提交顺序倒序**的多进程。回放与对照回放各一组。
3. **"倒序"的定义（M-07）**：倒序作用于**实际提交给进程池的任务序列**：
   - 回放：`tasks` 列表；
   - 对照回放：`group_plan` 与按组排序**之后**、提交给 `pool.map` 的组序列。

   不得只倒序一个随后会被重新排序的列表。实现时把"构造提交序列"抽成一个函数，测试断言倒序运行时提交的序列确实是正常序列的逆序。组内的计算顺序由 `group_plan` 的依赖决定，本卡不改。
4. **判定**：每个检查键，所比较的各模式的全语义摘要必须完全相同（正式运行按第 2 项的模式；专用测试按四种模式）；离散摘要照旧比较。
   - `manifest` 的 `i17_check` 每条记录：原有的 `equal` 字段保留，新增 `semantic_equal`。
   - `i17_ok` 要求：每条记录的两项都为真，并且没有缺项。
   - **对照回放的清单字段顺序**（G-M0b-01）：`compare/service.py` 用 `_MANIFEST_ORDER` 给 `manifest` 排序，不在其中的键会使运行报错。新增的 `i17_expected_keys`、`i17_missing_keys` 必须同时加入 `_MANIFEST_ORDER`，位置紧跟 `i17_ok`。测试中断言对照回放能写出含这两个键的清单。
5. **文档**：回放与对照回放的说明文档（15、16 号）同步修改，写明新增字段与判定规则。

**测试**：
- 用合成数据的单元测试覆盖四种模式。
- 人为让其中一种模式的某个非离散字段不同，例如 `atr_ep` 加最后一位：检查 `semantic_equal` 为假、`i17_ok` 为假。
- 人为去掉一个预期检查键：检查 `i17_ok` 为假，并且 `i17_missing_keys` 列出这个键。
- 断言倒序运行时提交的序列是正常序列的逆序（MR-03）：
  - 回放与对照回放的倒序测试，各自至少包含两个不同的实际提交任务或组；
  - 除断言互为逆序外，还要断言正常序列与倒序序列**不相同**；
  - 摘要按检查键对齐后比较，不按结果列表的位置比较。
- **表述限制**：文档与回执中只能写"正式回放为固定抽样的三模式检查；正式对照回放为固定抽样的两模式检查；四模式与倒序提交由专用合成测试检查"，不得写成"真实数据全集已通过四模式验证"。

**比较的口径（M-05）**：
- 截断点 T 一律**严格早于完整运行的观察终点**。观察终点的截尾（`runner._censor`）会改写最后一日的 `end_reason`、清空 `final_state.episode`，并设置 `censored_episode`。T 早于终点时，完整运行的对应前缀里没有截尾。
- 设完整运行为 `full`，截到 T 的前缀运行为 `part`，k = `len(part.results)`。"未截尾的对应前缀"定义为：
  - `results` = `full.results[:k]`；
  - `final_state` = `full.results[k − 1].state`；
  - `censored_episode` = 空。
- `part` 必须与这个对应前缀逐字段相同，**不排除任何字段**，全语义摘要也相同。
- 本卡不比较观察终点当日的截断。

## 4. 领域层纯净的自动检查（红线 5）

新增 `tests/unit/test_domain_purity.py`，用 `ast` 扫描 `src/stock_risk/domain` 下全部 `.py` 文件。

**说明**：这是静态护栏，只检查源码中的写法。它不能证明任意 Python 代码都是纯净的。例如以变量传入的种子是否合法，仍由调用方的入口契约保证。测试文件开头写明这一点。

1. **导入白名单**：
   - 只允许以下标准库模块，以及 `stock_risk.domain` 自身：
     `__future__`、`bisect`、`collections`、`collections.abc`、`dataclasses`、`datetime`、`decimal`、`enum`、`functools`、`hashlib`、`itertools`、`json`、`math`、`random`、`re`、`statistics`、`typing`。
   - 出现其他模块即失败。白名单要增加模块时，由产品经理批准，并写进本测试的注释。
   - **通配导入**（`from x import *`）一律拒绝。
2. **别名解析（M-02）**：先解析每个文件的 `import` 与 `from … import`，记下别名与原名的对应关系，例如 `import random as r`、`from random import choice as pick`、`from datetime import datetime as dt`。下面第 3 项的规则按**原名**判断。
3. **禁止的写法**：
   - 内置函数 `open`、`print`、`input`、`eval`、`exec`、`__import__`、`breakpoint`；
   - **读取当前时间（M-01）**：对 `datetime`、`date` 调用 `now`、`today`、`utcnow`；
   - `utcfromtimestamp`：它返回不带时区的时间，结果依赖本机时区的解释；
   - 不带时区参数的 `fromtimestamp`：依赖本机时区；
   - `random` 模块的模块级函数，例如 `random.random()`，或经 `from random import choice` 导入的 `choice`；`SystemRandom`；
   - `Random()` 不带参数，或者种子写成字面量 `None`：`Random(None)`、`Random(seed=None)`；
   - **动态取属性**（G-M0b-05）：`getattr`、`hasattr` 的第一个参数按别名解析后是 `datetime`、`date`、`time`、`random` 模块，或者是 `datetime`、`date`、`Random` 类的，一律禁止。领域代码中对自身对象使用 `getattr` 是现有的合法写法（`aggregate.py`、`params.py` 等），不受影响。
4. **允许的写法（M-01）**：带显式 UTC 时区的时间戳转换，例如 `datetime.fromtimestamp(x, tz=UTC)` 或 `tz=timezone.utc`。它只转换输入的时间戳，不读取时钟。时区可以用关键字 `tz=` 传入，也可以作为第二个位置参数传入（G-M0b-05）。
   - 现有的 `domain/massive_paid.py` 中 `bar_day` 就属于这一类，应当通过。
   - 时区参数必须是 `UTC` 或 `timezone.utc`（按别名解析后的原名判断），其他时区一律拒绝。
5. **自检**：测试中各写一段源码字符串，送入同一个检查函数：
   - 每条禁止规则至少一例，断言能检出，其中包括：
     - `import random as r; r.random()`；
     - `from random import choice as pick; pick(x)`；
     - `from random import *`；
     - `Random(None)`；
     - `from datetime import datetime as dt; dt.now()`；
     - 不带时区的 `fromtimestamp`；
     - `fromtimestamp(x, tz=other_tz)`；
     - `getattr(datetime, "now")()`；
   - 允许规则至少三例：`tz=UTC`、`tz=timezone.utc`、位置参数 `fromtimestamp(x, UTC)`，断言不会误报；另加一例对普通对象的 `getattr(self, name)`，断言不会误报。
6. **现有代码应当全部通过**。如果不通过，停止并报告。不得修改领域代码去迁就检查，也不得放宽检查。

## 5. 逐字节确定性（红线 5，M-08）

先列出已知会嵌入运行元数据的位置（产品经理已核对代码）：
- `daily`、`events`、`episodes` 的 CSV 中都有 `run_id` 列；
- 图表数据的标题包含 `run_id`；
- `manifest` 中有 `run_id`、`started_at`、`finished_at`、`elapsed_seconds`、`git`。

**测试入口**（G-M0b-04）：两项测试都调用 `ReplayRunService.run_reference`。只有这个入口会写出 `daily`、`events`、`episodes` 与图表四类目标文件，而且它的清单中没有 `parallel_seconds`。时钟用测试中给定的**固定时间序列**，按调用次数依次返回，不读取真实时间。

**测试一：相同元数据，逐字节相同**
- 用同一个固定时间序列、相同的提交信息、相同的 `run_id`，把同一份输入（AAPL、NFLX）以 `run_reference` 回放两次，输出到两个隔离的根目录。
- 两次的**文件清单**相同，**每个文件的全部字节**相同，包括 `manifest` 与运行索引。
- **唯一允许的处理**：如果某个文件嵌入了输出根目录的路径，先把两个根目录的路径字符串分别替换为同一个占位符，再比较字节。除此之外不做任何替换或删除。
- 有任何其他差异，停止并报告。

**测试二：只改运行元数据，业务不变**
- 在测试一的基础上，只改变 `run_id` 与固定时间序列的取值（开始、结束时间），调用次数与顺序不变。
- 每个（对象，候选）的全语义摘要不变。
- 文件差异只允许出现在下列**事先列明的字段路径**上，测试中逐个写出：
  - CSV 的 `run_id` 列；
  - 图表标题中的 `run_id` 子串；
  - `manifest` 的 `run_id`、`started_at`、`finished_at`、`elapsed_seconds`；
  - 运行索引中的 `run_id`；
  - 输出目录名。
- 比较时把这些字段**逐个**置为同一个占位值后，再比较其余内容。不得删除整个嵌套对象来消除差异。
- 参数、数据哈希、配置哈希、事件依据、检查覆盖清单（第 2 节的预期键与缺项）都**不是**可忽略的元数据。
- 如果出现上述清单以外的差异，停止并报告，由产品经理决定是否补入清单。不得由执行者自行补入。

**适用范围**：在 19 号或 15 号文档中写明"同一 Python 版本、同一平台、同一依赖锁定"。跨平台的浮点末位差异不在本卡范围内。

## 6. 旧 Tiingo 工具拒绝复用未经验证的目录（F-06 ②）

**问题**：`fetch_batch` 按状态跳过"已完成"的代码，但不记录当时请求的区间与来源。在同一目录扩大区间再运行时，会静默漏下载。另外，`state_of` 对成功记录只检查文件是否存在，不验证内容，文件被截断或替换后仍会被跳过。

**改法**：只在 `application/fetch_batch.py` 及其存储端口、存储实现中实现，不扩建其他功能。

1. **请求记录**：目标目录中新增一份请求记录文件，文件名在实现中确定，并写进 02 号文档。内容：
   - 数据源名称；
   - 每个代码的 `source_ticker`、`start`、`end`；
   - 每个已完成代码的完成结果：
     - `ok`：价格文件 `<SYMBOL>.csv` 与公司行动文件 `<SYMBOL>.actions.csv` 各自的 SHA-256（G-M0b-02）；
     - `no_data`：只记请求身份，不要求有任何文件；
   - 已追加进记录但尚未完成的代码，标为"未完成"。
2. **运行开始时判定**：在发出任何请求之前完成判定。被拒绝的运行：退出码非 0，0 次请求，目录中的任何文件都不改动。

   | 目录情形 | 处理 |
   | --- | --- |
   | 没有状态文件、没有数据文件、没有请求记录（新目录） | 写入请求记录，照常运行 |
   | 有状态文件或数据文件，但没有请求记录（旧目录） | **拒绝** |
   | 有请求记录，但记录中的**数据源名称**与本次不同 | **拒绝**。每次运行都要核对，与本次清单中是否都是新代码无关（M-09） |
   | 本次清单中的某个代码在记录里，但 `source_ticker`、`start` 或 `end` 任一项不同 | **拒绝** |
   | 本次清单中的某个代码在记录里且身份一致，记录为 `ok`，但价格文件或公司行动文件缺失，或者任一 SHA-256 不符（M-10、G-M0b-02） | **拒绝**，报告该代码、哪个文件与原因。本卡不自动重新下载 |
   | 本次清单中的某个代码在记录里且身份一致，记录为"未完成"或失败（上次请求报错，或者因 429 中途退出），并且目录中**没有**它的价格文件与公司行动文件（G-M0b-02） | 照常重新请求，完成后更新记录 |
   | 同上，记录为"未完成"或失败，但目录中**有**它的价格文件或公司行动文件 | **拒绝**：文件来历不明，不得当作这次请求的结果 |
   | 本次清单中的某个代码**不在记录里**，但目录中已有它的价格文件或状态记录（M-09） | **拒绝**：这是未经验证的旧数据，不得包装成新请求 |
   | 本次清单中的某个代码不在记录里，目录中也没有它的任何文件或状态 | 照常请求；请求之前追加进记录 |
   | 本次清单中的代码在记录里，身份一致，`ok` 的两个文件哈希都相符 | 跳过，0 次请求 |
   | 本次清单中的代码在记录里，身份一致，记录为 `no_data`，目录中没有它的任何文件 | 跳过，0 次请求 |
   | 同上，记录为 `no_data`，但目录中有它的价格文件或公司行动文件（MR-02） | **拒绝**：与"无数据"矛盾，报告该代码 |

3. 每个代码完成时，把完成结果写入记录：`ok` 带两个文件的哈希，`no_data` 不带。
4. **统一的完成判定**（MR-01）：
   - 写一个判定函数：只有请求记录中身份一致，并且记录为 `ok` 且两个文件的哈希都相符，或者记录为 `no_data` 且没有矛盾文件，才算"已完成"。
   - 这个函数**同时用于**三处：跳过已完成的代码、`cumulative_done`、`remaining`。现有按 `_fetch_status.json` 判断的 `state_of` 不再单独决定"已完成"。
   - 请求记录为"未完成"或失败时，即使旧的 `_fetch_status.json` 写着 `ok` 或 `no_data`，也按未完成处理，不得被旧状态覆盖。
5. **关联文件**（MR-02）：凡是第 2 项判定表中说"文件"的地方，都指价格文件 `<SYMBOL>.csv` 与公司行动文件 `<SYMBOL>.actions.csv` 两者，任一存在即算"有文件"。
6. 报错信息写明哪个代码、哪一项不一致，或者"旧目录没有请求记录"，并建议改用新目录。
7. `fetch-raw-data`（探索期下载）不在本卡范围内。

**测试**：用合成存储与假数据源，每种情形都断言请求次数；拒绝的情形还要断言目录中全部文件逐字节不变。
- 新目录：照常运行；请求记录写入，`ok` 带哈希。
- 旧目录：拒绝。
- 区间扩大（ChatGPT 的复现例：先请求 2012-01-01—2012-12-31，再请求 2008-01-02—2019-12-31）：拒绝。
- `source_ticker` 变化：拒绝。
- 数据源名称变化，并且本次清单全是新代码：拒绝。
- 价格文件被截断：拒绝；价格文件被删除：拒绝；公司行动文件被删除或改动：拒绝。
- 上次因假数据源报错而记为失败的代码，身份一致、没有残留文件：重新请求 1 次，完成后记录更新为 `ok` 并带两个哈希。
- 上次在请求之前已追加进记录、随后因 429 中途退出的代码：同上，重新请求。
- 记录为失败、目录中却有它的价格文件：拒绝。
- 记录只有 AAA，目录中却有 BBB 的价格文件，本次请求 BBB：拒绝。
- 记录一致：跳过已完成的代码，0 次请求。
- `no_data` 的代码再次请求，身份一致：跳过，0 次请求；不要求有价格文件。
- 真正的新代码：只请求新代码，并追加进记录。
- 新代码在目录中只有孤立的 `<SYMBOL>.actions.csv`：拒绝（MR-02）。
- 记录为 `no_data`、目录中却有它的公司行动文件：拒绝（MR-02）。
- 请求记录为"未完成"、旧 `_fetch_status.json` 为 `no_data`、没有文件：重新请求 1 次，不被旧状态跳过（MR-01）。
- 同上情形，但每日请求额度已用完、未能重试：运行正常结束，该代码仍计为未完成，`remaining` 包含它（MR-01）。
