## 1. 补正项

### C-01 禁止自动重定向（阻断以后的真实请求）

**问题**：`infrastructure/massive/client.py` 的默认传输层使用 `urllib.request.urlopen`。它会自动跟随重定向，并把 `Authorization` 请求头带到新的主机。现有的主机检查只覆盖初始地址与 `next_url`。

**改法**：
- 默认传输层改用自建的 opener，其中的重定向处理器**遇到任何 3xx 都不跟随**，抛出项目的数据源错误。Massive 的接口不需要重定向。
- 错误信息写明状态码与目标主机，不写请求头。
- 免费档与付费档都适用。

**测试**：
- 在测试中启动一个只监听 127.0.0.1 的本地 HTTP 服务，路由分别返回 301、302、303、307、308，都指向另一个本地端口上的第二个服务。
- 用**真实的默认传输层**发出请求，对每种状态码断言三点：
  - 抛出错误；
  - 第二个服务没有收到任何请求；
  - 错误信息中不含认证头或密钥。
- 不得只用注入的假传输层来测这一项。

### C-02 h 窗口被下一事件截短时，可确定日要等下一事件的标签（阻断 E4–E6 的两段归属）

**问题**：`domain/evaluation/windows.py` 中计算 h 窗口时，即使窗口终点被下一事件的峰值截短（t\_h = 下一峰值 − 1），也传入 `truncated_by_next=False`。结果是 `membership.window_determinable` 不等待下一事件的标签。

**改法**：按窗口是否**实际**被截短传值。截短的条件是：存在下一事件，并且下一峰值日 − 1 < k + Y\_max（原始目标终点）。**恰好相等不算截短。**S2 窗口的现有写法（按 D 类判定）不变，但要核对：S2 窗口是否也存在"实际被截短、却不是 D 类"的情形；有的话，停止并报告。

**可确定日的规则**（17 号第 2.2 节）：
- 窗口被截短时，可确定日 = max(本事件标签的可确定日, 下一事件标签的可确定日)；
- 下一事件的标签不可确定时，为空；
- **归段规则**（R2-03，本卡统一规定）：可确定日为空的指标，**一律记 NEITHER**，不归入任一段。
  - 依据：可确定日为空，说明无法证明这个指标只用到了某一段的数据。17 号第 5.3 节只写了"峰值在前段、所需数据延伸到后段"记 NEITHER；峰值在后段而可确定日为空的情形，17 号没有明写，本卡按同一原则处理。
  - 现有的 `membership` 归段函数在可确定日为空时返回 BACK，要相应修改。
  - **测试**：覆盖下表五种情形，期望值按本规则给出。

    | 峰值所在段 | 可确定日 | 期望 |
    | --- | --- | --- |
    | 前段 | 为空 | NEITHER |
    | 后段 | 为空 | NEITHER |
    | 前段 | 不晚于分界日 | FRONT |
    | 前段 | 晚于分界日 | NEITHER |
    | 后段 | 非空 | BACK |

**回归测试**（期望值由产品经理给出）：
1. **夹具 A04**：
   - 本事件标签的可确定日为第 354 日；
   - 下一事件的峰值日为第 354 日，所以 h 窗口目标终点为第 353 日，窗口被截短；
   - 下一事件在数据终点仍未确认，标签不可确定。

   期望：h 指标的可确定日为空。
2. **构造用例**：在 A04 的价格之后接上数据，使下一事件在第 T 日确认，并且它没有前序事件晚于 T 确认。期望：h 指标的可确定日 = max(354, T)。执行者构造价格时，T 取一个确定的值，在回执中写出构造方法与 T。期望值按上述公式计算，不取实现的输出。

### C-03 公司行动分页未完成，不得记为成功

**问题**：`application/probe_massive_paid.py` 的 `_run_actions` 不检查拆股与分红分页的 `complete` 标志。

**改法**：
- 拆股与分红任一分页未完成的，状态记为 `incomplete`，保存已取得的部分，并在 `summary.json` 中单列。
- 这类记录不得用于复权计算，也不计入"齐全"的统计。
- **同步核对** `application/verify_massive_relay.py` 的全部分页调用，包括价格与参考清单：凡是没有检查 `complete` 标志、或者恢复时只看进度键是否存在的，按同样规则修改（G-V3-02）。

**恢复策略**（R2-05）：
- 标为 `incomplete` 的项目，下次运行时**重新获取**；
- 剩余清单区分"已完整完成"与"已尝试但不完整"，后者计入剩余项。

**测试**：
- 拆股不完整、分红不完整各一条；
- **两次运行**：第一次分页不完整，第二次完整。断言最后的状态为完整，保存的内容为第二次的完整结果，剩余项为 0。

### C-04 任何接口返回 401 或 403，都停止整个运行

**问题**：现在只有日线请求的 401、403 会停止运行；拆股、分红、清单与证券详情返回 401、403 后，运行还会继续。

**改法**：
- 付费档的 `probe-massive-paid` 与 `verify-massive-relay` 两个命令，任何请求返回 401 或 403，都保存进度后停止整个运行，再次运行时不发请求。这与 02 号的规定一致。
- 02 号中的相应说明同步更新，写明适用于全部接口。

**测试**（G-V3-02），401 与 403 各测一次：
1. `probe-massive-paid`：拆股返回 401 或 403 后停止，此后不再发出任何请求；**第二次运行时发出 0 次请求**。
2. `verify-massive-relay`：一个非价格请求（参考清单或证券详情）返回 401 或 403 后停止，并持久化停止状态；第二次运行时发出 0 次请求。

### C-05 不利条件分别判定，已知成立的不被缺失吞掉

**问题**：`domain/evaluation/release_windows.py` 中，ATR 或 L\_ep 任一不可得，整个"是否不利"就返回空，即使其他条件已经确定成立。

**改法**：三个条件分别判定，每个条件的结果为成立、不成立或未知：
- 跌幅 ≥ y\_pct；
- 跌幅按 ATR 计 ≥ y\_atr；
- 收盘 < L\_ep。

整体按以下规则合成：

| 情形 | 是否不利 |
| --- | --- |
| 窗口内任一日、任一条件已知成立 | 是 |
| 全部日子、全部条件都已知不成立 | 否 |
| 其他 | 未知，附原因代码（`ATR_UNAVAILABLE`、`L_EP_UNAVAILABLE` 等） |

**原因代码的合成规则**（G-V3-01）：缺失的输入（`ATR_UNAVAILABLE`、`L_EP_UNAVAILABLE`）与未走完的窗口（`INCOMPLETE_WINDOW`），**无论结论是否已经确定，一律记入原因字段**。原因字段说明的是"输入状况"，不是"结论为什么未知"。

**首个不利日**：取已知成立的最早一日 d\*。但如果 d\* 之前有某一日存在"未知"的条件（那一天可能已经不利），首个不利日记为空，加原因 `FIRST_DAY_UNCERTAIN`。

**字段**（R2-06）：现有的 `criteria`（首个不利日满足的条件）拆成两个字段：
- `known_criteria`：在已观察部分中**已知成立过**的条件；
- `first_criteria`：首个不利日满足的条件；首个不利日为空时，这一字段也为空。

**窗口不完整时**：
- 已观察部分中已知成立的，判定为不利，这一结论不受未观察日子的影响；
- 已观察部分中没有已知成立的，记为未知，原因 `INCOMPLETE_WINDOW`，不判定为"否"。
- 主口径的分母仍只用完整窗口（17 号），不变。

`thresholds` 未给定时，行为不变：不判定，原因为 `NO_THRESHOLDS`。

**测试**（产品经理推导）：
1. **ATR 不可得，但跌幅条件成立**：
   - 输入：C\_r = 100；窗口内收盘依次为 98、70、72；L\_ep = 95；y\_pct = 0.2；y\_atr = 3；A\_r 不可得。
   - 推导：
     - 第 1 日：跌幅 0.02 < 0.2，不成立；98 ≥ 95，不成立；ATR 条件未知。
     - 第 2 日：跌幅 0.30 ≥ 0.2，成立；70 < 95，成立。
   - 期望：是否不利 = 是；`known_criteria` = {跌幅, 跌破 L\_ep}；首个不利日 = 空，`first_criteria` = 空，原因 `FIRST_DAY_UNCERTAIN`（第 1 日的 ATR 条件未知）。
2. **同上，但第 1 日的收盘为 70**：
   - 输入：收盘依次为 70、70、72，其余同用例 1。
   - 期望：是否不利 = 是；首个不利日 = 第 1 日（之前没有日子）；`known_criteria` = {跌幅, 跌破 L\_ep}；`first_criteria` = {跌幅, 跌破 L\_ep}；原因含 `ATR_UNAVAILABLE`。
3. **ATR 不可得，其他条件都不成立**：
   - 输入：收盘依次为 99、98、97；L\_ep = 95；y\_pct = 0.2。
   - 期望：是否不利 = 未知；原因含 `ATR_UNAVAILABLE`。
4. **L\_ep 不可得，但跌幅条件成立**：
   - 输入：C\_r = 100；收盘依次为 70、72、75；A\_r = 5；y\_pct = 0.2；y\_atr = 3；L\_ep 不可得。
   - 推导：第 1 日跌幅 0.30 ≥ 0.2，成立；ATR 倍数 30 ÷ 5 = 6 ≥ 3，成立；L\_ep 条件未知。
   - 期望：是否不利 = 是；首个不利日 = 第 1 日（之前没有日子）；`first_criteria` = {跌幅, ATR}；原因含 `L_EP_UNAVAILABLE`。
5. **阈值未给定**：
   - 期望：是否不利 = 空；原因 `NO_THRESHOLDS`；两个条件字段都为空。
6. **窗口不完整**：
   - 输入：Q = 5，只观察到 3 日，收盘依次为 99、98、97；C\_r = 100；A\_r = 5；L\_ep = 95；y\_pct = 0.2；y\_atr = 3。
   - 推导：三日三个条件都已知不成立，但窗口不完整。
   - 期望：是否不利 = 未知；原因含 `INCOMPLETE_WINDOW`。
   - 另一例：观察到的收盘依次为 99、70、97，其余同上。
     - 推导：第 1 日三个条件都已知不成立；第 2 日跌幅 0.30 ≥ 0.2，ATR 倍数 30 ÷ 5 = 6 ≥ 3，70 < 95，三个条件都成立。
     - 期望：是否不利 = 是；首个不利日 = 第 2 日；`known_criteria` = `first_criteria` = {跌幅, ATR, 跌破 L\_ep}；原因含 `INCOMPLETE_WINDOW`。
