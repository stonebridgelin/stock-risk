## 1. 要实现的内容

### 1.1 方法状态的完整性（17 号第 4 节第 1.2 节，RL-05）

新增一个表示方法状态完整性的类型，取值为：
- `COMPLETE`：逐日输出与评价日历完全对应；
- `NOT_RUN`：未运行；
- `FAILED`：运行失败；
- `MISALIGNED`：缺日、日期错位或顺序不同。

**判定**：
- 方法序列的 `days` 与 `EvalSeries.calendar.days` 逐项相等（同样的日期、同样的顺序、没有缺日），才是 `COMPLETE`；
- 没有方法序列的，按调用方给出的 `NOT_RUN` 或 `FAILED` 处理。

不得用"不在警"填补任何不完整的状态。

### 1.2 单个事件的分类（第 1.0 节，"先判定，后分类"）

建议的函数签名如下（可以调整，但输入与行为不变）：

```
classify_h1(event, f_ref, judged, method_state, data_end) -> H1Unit
```

其中：
- `judged`：现有 `judge_h1` 的结果。`method_state` 不是 `COMPLETE` 时为空，并且**不得**调用 `judge_h1`；
- `data_end`：评价日历的最后一日。

**入口契约**（G-T13-01、T13R-02）：进入分类之前先校验，任一项不成立即抛错，按工程错误处理（17 号第 5.4 节），不归入任何类别：
- **双向等式**：`f_ref.searched == (event.is_main or event.is_prefix_complete)`。与 `find_f_ref`（`h1.py` 第 63–81 行）一致：主口径或前缀完整的事件一定搜索，其余事件一定不搜索；
- 未搜索时：`f_ref.day` 必须为空，且 `f_ref.reasons` 必须与 `outcomes.exclusion_reasons(event)` 完全相等；
- `f_ref.day` 不为空时，`f_ref.searched` 必须为真。

原因集合的分类（第 3 步的"每个代码是否满足第 1.3 节"）另写成一个独立的纯函数，供入口之后调用，也单独测试。

按下面的顺序，取第一个适用的步骤：

1. **能判定的，照常判定**：`f_ref.searched` 为真，且 `f_ref.day` 不为空。包括主口径事件，以及前缀完整的右端截尾事件。
   - `method_state` 是 `COMPLETE`：结果取 `judged.status`，即 OK 或 VIOLATION；
   - 否则：**乙类**，原因 `METHOD_STATE_UNKNOWN`，并附上完整性状态；
   - 退市截尾的事件，只要满足这一步，就照常判定，不进入甲类。
2. **已知不适用**：`event.is_main` 为真，`f_ref.searched` 为真，且 `f_ref.day` 为空。结果为 NOT\_JUDGED，不计入应检单位。
3. **其余事件**：
   - 原因集合 = `outcomes.exclusion_reasons(event)` ∪ `f_ref.reasons`。不得只用 `H1Result.reasons`；
   - 原因集合非空，且**每个**代码都满足第 1.3 节的条件：**甲类**，按原因类别计数；
   - 原因集合为空，或者有任何一个代码不满足：**乙类**；
     - 只有 `DEPENDENCY_PENDING` 核实不了时，原因记 `DEPENDENCY_UNVERIFIED`；
     - 其余情形，原因记 `UNRECOGNIZED_REASON`，并列出全部未识别的代码；原因集合为空时，列为空；
     - 两种情形同时出现时，两个原因都记，未识别的代码也全部保留。

**`H1Unit` 至少包含以下字段**：
- 单位身份（第 1.5 节）；
- 单位种类：事件或区间；
- 方法名；
- 结果：OK、VIOLATION、乙类、甲类、NOT\_JUDGED、`NOT_APPLICABLE_NO_DAILY_STATE`（只用于 B3，见第 1.7 节）；
- 原因代码集合；原因类别集合（只有甲类有）；
- 乙类的原因（`METHOD_STATE_UNKNOWN`、`UNRECOGNIZED_REASON`、`DEPENDENCY_UNVERIFIED`）与未识别的代码；
- 方法的完整性状态；
- 归属日期：事件单位取 p；区间单位取它所依赖事件的 p。

### 1.3 已识别的原因代码（第 1.1 节的表）

只认下表中逐字列出的代码字符串。今后新增的 `RIGHT_…`、`UNEVALUABLE_…` 等代码，不会自动视为已识别。

| 代码 | 原因类别 | 条件 |
| --- | --- | --- |
| `RIGHT_DELISTED` | 退市 | 无 |
| `MISSING`、`DATA_BREAK`、`UNEVALUABLE_MISSING` | 缺价 | 无 |
| `UNEVALUABLE_WARMUP` | 预热 | 由第 1.8 节在事件生成时证明 |
| `RIGHT_DATA_END`、`RIGHT_REQUIRED_END`、`RIGHT_PERIOD_END` | 右截尾 | 无 |
| `F_REF_ABSENT` | 跟随同一原因集合中的 `RIGHT_*` 代码：有 `RIGHT_DELISTED` 归退市，否则归右截尾 | 原因集合中**至少有一个**上面列出的 `RIGHT_*` 代码；没有就不满足 |
| `DEPENDENCY_PENDING` | 跟随事件自身的 `RIGHT_*` 代码：`RIGHT_DELISTED` 归退市，其余归右截尾 | 见下 |

`UNEVALUABLE_UNKNOWN`（第 1.8 节新增）**不在表中**，所以一律归乙。

**`DEPENDENCY_PENDING` 的核实条件**：

依赖对象是事件本身。按 `events.py` 第 148–154 行，依赖未决区间挂在"数据终止时仍在待确认"的那个事件上，区间为 (e, 数据终点]。以下各项**全部**成立，才满足条件：

1. `event.dependency_pending` 不为空；
2. `event.confirm` 为空，且 `event.e` 不为空；
3. `dependency_pending.start_exclusive == event.e`；
4. `dependency_pending.end_inclusive == data_end`；
5. `event.censor` 中**恰好有一个** `RIGHT_*` 代码，并且它在上表中。

这五项按现行 `events._label` 的生成路径写成。输入必须来自同一条事件链，不接受拼接来的事件。

任何一项不成立，都是"有疑义"：
- 事件单位按第 1.2 节第 3 步归乙，原因 `DEPENDENCY_UNVERIFIED`；
- 它的区间单位（如果非空）也归乙，原因相同。

### 1.4 区间单位

- **生成条件**：每个带 `dependency_pending` 的事件，若区间**非空**（`start_exclusive < end_inclusive`），生成一个区间单位。
  - 是否为空按边界判断，**不按** `valid_days` 判断；
  - 非空但 `valid_days` 为 0 的，也生成区间单位。
- **分类**（T13R-01）：第 1.3 节的核实条件全部成立的，区间归甲类；类别由所依赖事件已核实的、唯一的 `RIGHT_*` 截止原因**独立确定**：`RIGHT_DELISTED` 为退市，其余已识别的 `RIGHT_*` 为右截尾。**不复制**事件单位的其他类别（例如缺价、预热），也不受事件单位结果（例如 VIOLATION）的影响。核实条件不成立的，区间归乙类，原因 `DEPENDENCY_UNVERIFIED`。
- 区间单位与方法无关，对每个方法都相同。
- 另记该区间的有效日数（`valid_days`）。证券日数由应用层汇总。

### 1.5 单位身份、预期单位清单与预期方法名单（第 1.3 节）

- **事件单位的身份**：（证券代码，事件集名称，s，p）。
- **区间单位的身份**：（证券代码，事件集名称，依赖事件的 s，依赖事件的 p，`start_exclusive`，`end_inclusive`）。
- **预期单位清单**：对每个证券、每个事件集，只由事件链生成，与任何方法无关。包括全部事件，含截尾与不可评估的事件，以及全部非空的区间。
- **预期方法名单**（T13-04）：由调用方显式给出，例如 R0、B1、B2、B3 与各候选。
  - 未运行或运行失败的方法，也必须在名单中，并以 `NOT_RUN` 或 `FAILED` 照样生成全部单位：第 1 步的单位为乙类，其余单位按事件链分类；
  - 不得因为方法没有结果就从检查中整组消失。
- **检查函数**（运行时不一致即抛错，按工程错误处理）：
  1. **方法集合**：收到的方法集合与预期方法名单完全相同，不缺、不多；
  2. **覆盖**：每个方法的结果恰好覆盖预期清单中的全部单位，不漏、不重、不多出清单外的单位；
  3. **跨方法一致**：所有方法（含 B3）的甲类单位集合逐件相同，比较的内容是单位身份加原因类别集合；
  4. **空清单**：预期清单为空时，函数照常返回空结果；测试中要明确断言"为空"。

### 1.6 汇总：应检单位、四个比例与敏感性（第 2 节）

对每个事件集、每个方法，在一个给定期间内汇总。期间按单位的归属日期判断，用左闭右开区间表示，例如开发期为 [2010-01-01, 2020-01-01)。

**应检单位**：
- 事件单位：OK、VIOLATION、乙类、甲类；
- 区间单位：甲类与乙类；
- **不含** NOT\_JUDGED，但另报它的数量；
- 汇总只接受有逐日状态的方法。方法的种类标记为"无逐日状态"（B3）时，汇总函数**直接抛错**，不返回任何计数、比例或上限结论（G-T13-02）。B3 只进入第 1.5 节的覆盖与跨方法一致检查。

**输出**：

1. **计数**：
   - 应检事件单位数、应检区间单位数；
   - OK、VIOLATION、乙类（按原因分列）、甲类（事件与区间分列）的数量；
   - 各原因类别的单位数（事件、区间分列，可以重叠）；
   - NOT\_JUDGED 的数量。
2. **用于资格的违反数**：VIOLATION 加乙类（事件与区间都算）。乙类在报告中与 VIOLATION 分开列出，但计数合并。
3. **四个比例**，以精确分数表示（分子、分母都保留），同时给出按 `decimal_ratio.q12` 量化的 12 位小数：

   | 比例 | 分子 | 分母 |
   | --- | --- | --- |
   | ① 事件级甲类比例 | 甲类事件单位数 | 应检事件单位数 |
   | ② 混合甲类比例 | 全部甲类单位数 | 全部应检单位数 |
   | ③ 事件级退市比例 | 原因类别含退市的甲类事件单位数 | 应检事件单位数 |
   | ④ 混合退市比例 | 原因类别含退市的全部甲类单位数 | 全部应检单位数 |

   分母为 0 的比例记"不可判定"，不填 0。

4. **敏感性**：把全部甲类单位按违反计，即违反数 + 甲类单位数。只作描述。

**上限的输入与比较**（G-T13-03）：
- U\_甲、U\_退市以 `Decimal` 传入。入口拒绝：`float`、非有限值（NaN、无穷）、小于 0 或大于 1 的值；
- 入口用 `Decimal.as_integer_ratio()` 把上限转为整数对 (a, b)，比例本身就是整数对 (n, d)；
- 先判分母：d = 0 的比例记"不可判定"，不进入比较；
- 比较只用 Python 整数交叉相乘：n × b ≤ a × d 即"不超过"；
- 不经过 `float`，不在比较前做任何量化；
- 不使用 `fractions`：它不在领域层的标准库白名单中。

**上限判定**：
- 函数参数 `caps` 为必填，但可以传"未批准"。传"未批准"时，只输出比例，判定结论为"上限未批准，只展示"。
- 传入已批准的 U\_甲、U\_退市时：① 与 ② 各自不得超过 U\_甲，③ 与 ④ 各自不得超过 U\_退市。
  - "不得超过"即等于上限也算通过；
  - 按上一段的整数交叉相乘比较，不用量化后的小数比较；
  - 任一比例超过上限：结论为"证据不足"；
  - 任一比例不可判定：结论为"不可判定"，不称上限内；
  - 这是 17 号第 2 节第 3 项"拟议的判定方式（待批准）"，代码按拟议实现，批准状态由调用方的参数表达。
- **上限判定结论与 H1 违反数分别输出。** "上限内"只说明甲类比例没有超限，不说明 H1 通过；H1 通过还要求违反数为 0。

**查看限制**（第 2 节第 5 项）：
- 汇总函数要求调用方给出数据集的角色：探索集、选参集或验证集；
- 选参集与验证集的角色下，`caps` 为"未批准"时**直接抛错**，不计算比例；
- 本卡不运行任何真实数据，这一护栏只用合成输入测试。
