## 1. 目标与边界

**探索期要回答的问题**：v0.7.1 生命周期规则在真实日线上能否做到"及时预警、及时降级与解除、每次变化说明依据"；哪些规则在真实行情中出现规格没有预料到的行为。

**产出**：

1. 一个严格按 v0.7.1 实现、通过全部适用夹具的生命周期引擎（domain 层，纯函数）；
2. 在 27 只个股上逐日回放（引擎自 2009-01-01 起运行，2008 年数据只作指标预热，2009 年为预热期）得到的事件表、每日状态表、预警摘要和交互图；14 个 ETF 只作背景参照（I15）；
3. 产品经理据此写出的"探索中发现"，作为规格 v0.8 的修订依据。

**不做**：

- 评价协议（规格第 5 节：事件集 E\_atr / E\_pct、S1 / S2、门槛、选参、基线、重采样）。这部分依赖 SR-M1 登记的数值，下一份计划再做。
- 数据库、推送、API、前端、每日调度；状态修正与衔接（规格第 1.6 节）。
- 任何 2020-01-01 及以后的数据。
- 本期回答的是**信号是否及时产生**，不是通知是否及时送达。

**研究阶段的边界（P-19）**：

- 本轮是**允许根据结果修改规则的探索阶段**。它会影响 SR-M1 要登记的数值和规则，因此由此得到的开发期表现不能当作独立证据。
- 后续的登记一律表述为"**探索后、验证期解封前冻结**"，不称为"看结果前登记"。本计划生效时即覆盖规格第 5 节"看任何结果前填写"的措辞，v0.8 再正式改写。
- 每轮探索保存 run\_id 与运行清单（I16），连同看过的候选、做出的修改及理由，写入 05 探索中发现，形成完整记录。
- 验证期（2020-01-01 起）保持封存，冻结后只运行一次。验证失败时，不得更换候选后把同一验证期再称为"未见过的数据"。

## 3. 关键实现决定（规格未写明之处，产品经理裁定，探索期适用）

这些决定先按下表执行，在规格 v0.8 中正式写入。Claude Code 不得自行另做选择。

| 编号 | 问题 | 决定 | 理由 |
| --- | --- | --- | --- |
| I1 | 交易日历 | 以 SPY 的交易日作为 NYSE 交易日历的代理；**T01 必须与独立日历核对**（I13） | SPY 每个 NYSE 交易日都有成交；正式日历版本留到 SR-M4 |
| I2 | 三个区间、缺价与左端（v2 修订，P-09、P-24） | 区分三个区间：**数据覆盖区间**（文件首日至末日）；**观察区间**（起点 = max(上市起点（若登记）, 数据首日)，终点见 I3）；**回放区间**（起点 = max(2009-01-01, 观察起点)，终点同观察区间）。观察区间内，日历上的交易日没有日线即为缺价；首条日线之前不算缺价。回放起点之前只计算缺价计数、历史段与指标（2008 年数据用于预热，使 2009-01-01 已可计算），**不产生预警，也不产生任何事件**；回放起点当日以"无预警"开始，按规格第 1.2 节逐日运行。左端分三类记录：`listing_start`（登记了上市日）、`request_start`（首日等于下载起点 2008-01-02，说明更早的历史是被请求范围截掉的）、`first_available`（首日晚于下载起点、又没有登记上市日，标"左端覆盖未核实"）。三类都可以从首日开始预热，但要在回放清单中披露 | 不能把数据源覆盖不足说成"上市前" |
| I3 | 右端与截尾（v2 修订，P-08） | 观察区间的终点 = min(探索截止日 2019-12-31, 登记的 `listed_until`)，**不取数据文件的末日**。终点之前文件提前结束 → 其后各交易日按缺价处理（可能触发 DATA\_ISSUE 与 DATA\_BREAK）。到达终点时仍在进行的预警标为截尾，终止原因分别记 `LISTING_END`（退市或被收购）、`EXPLORATION_END`（探索期末）；截尾不是 RELEASE，也不生成 DATA\_BREAK | 只有观察范围确实结束才截尾；数据源尾部缺失必须显示为缺价 |
| I4 | 价格口径 | 全部信号用复权价（adj\_\*），I11 登记的更正除外；原始价用于审计和以后的固定价止损 | v0.4 第 2.1 节 |
| I5 | 指标输入方式 | 生命周期引擎不自己算指标，通过 domain 内的指标接口取 ATR\_N、SMA10、开盘、收盘与前一交易日收盘；两种实现：由日线计算（回放与 F 组用）、按表给定（S 组用） | 夹具里 ATR、SMA10 是"给定输入"；同一引擎必须同时通过夹具和真实回放 |

| I7 | 回放候选（v2 修订） | 参考组合 N = 20、k₁ = 2、k₂ = 4、K = 3、d = 3、u\_rel = 3，乘以全部 12 种结构组合（confirm × release\_path × atr\_basis），共 12 组出图；768 组全部回放只出汇总。产品经理可以针对具体异常追加查看其他候选，查看原因记入 05 探索中发现 | 12 组用于首轮浏览，不足以单独代表结构优劣 |

## 6. 执行规则

1. **审阅先行**：计划与规格修改先经外部审阅，对应任务的阻断项解除后，产品经理再签发该任务卡。只涉及数据卫生或不依赖待审内容的任务，产品经理可以先签发，并在计划中写明理由；发起人可以否决。审阅采用"处置稿往返、收敛后一次落实"的方式：没有阻断项、重要项都有处置即收敛，只剩建议项不再等待。
2. **一卡一提交**：Claude Code 每张任务卡在本地提交，最后一次提交说明以任务编号开头；不推送，推送由发起人决定。
3. **回执**：每张任务卡结束时，按 `docs/tasks/README.md` 的格式输出回执，由发起人转给产品经理。
4. **不擅自决定**：遇到规格歧义、规格与夹具矛盾、需要业务数值时，停止该部分并写进回执，不自行假设。
5. **放行门槛（I14）**：T03 放行、T04 开始的条件是——全部适用夹具通过；有争议的夹具已经产品经理书面裁定、期望值已按 13 号文档第 5 节更新并复跑通过；不适用的夹具已在 13 号文档中写明。**只提交回执、列出不一致项，不能放行。**
