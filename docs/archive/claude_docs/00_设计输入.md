# 个股风险预警与反弹提醒项目：设计输入

Oct 13, 2026 · @stonebridge

新项目只做美国本土上市个股的风险提醒和止跌确认，不做预测；market-risk 是它的大盘背景来源，但要等 M3 之后才能每天供数。

本文是 market-risk 产品经理给新项目的设计建议，供多个 AI 智能体讨论设计时作为起点，不是已批准的设计。凡写“待定”的，都由新项目自己裁决；引用 market-risk 的规则和数值时，以其代码和白皮书为准。

## 第一部分：market-risk 能提供什么

market-risk 能给的是大盘背景、止跌确认事件和一套工程纪律；它现在还不能每天产出信号，个股项目先预留接口。

### 现状

- market-risk（波段预警 v2.0）目前只有研究回放能力，没有每日实时信号模块。第二道门、第四次正式运行、M3 都还没完成，θ、K、h 三个参数都未选定。
- 它是跟随确认式的：回撤已经达到 θ（1.5% / 2% / 2.5% 之一）才报警，另加一个交易日执行延迟。研究中没有发现显著的领先特征（样本少、统计功效低），不能指望它提前预测。

### 可供参考的数据（按价值排序）

| 数据 | 内容 | 对个股项目的用途 |
| --- | --- | --- |
| 大盘风险状态 | 每日：正常 / 一级 / 二级，是否在 4% 止损冷却期 | 市场背景层：区分系统性下跌与个股自身问题 |
| 通道原始值 | SPX、QQQ 距 63 日最高收盘价的回撤；SPX 是否低于 200 日均线及均线窗口是否完整；两资产距上次创 20 日新低的天数；当日五通道输入是否完整 | 写进提醒的解释文字；作为个股模型的输入特征 |
| 状态转换事件 | 正常→一级、一级→二级；二级→一级（两资产连续 K 天不再创 20 日新低且持续 h 天）；一级→正常（需 SPX 站上 200 日均线） | 二级→一级是“大盘止跌确认”，可作为个股反弹提醒的背景（待回测验证的假设）；一级→正常偏晚，不适合作反弹提醒 |
| 方法与工程纪律 | T 日收盘出信号、T+1 执行；输入非有限、缺失、长度不一致时明确失败；快升慢降的状态机；浮点容差 1e-10 与确定性复算；参数先登记再运行、独立复算、证据分两级、历史只追加 | 直接沿用 |

### 不应直接搬用的东西

- 研究组合仓位（正常 1.4 / 一级 0.6 / 二级 0.3）：属于 SPX+QQQ 研究组合，与个股持仓无关。
- 4% 组合止损：针对研究模型组合净值；个股波动差异巨大，固定 4% 没有意义。
- 参数选择规则（最大化 ln W）：为两资产组合设计，个股项目需要自己的评价指标。
- 研究结论：只在 SPX+QQQ 上评价过，不能外推到个股。

### 对接方式

- 单向、只读：market-risk 每日输出一份带版本的文件或数据表，含日期、状态、各通道值、输入完整标志、代码提交哈希、参数 θ / K / h。
- 个股项目不导入 market-risk 的内部模块，也不修改它，两边的证据链互不污染。
- 这个每日输出模块在 market-risk 里还不存在，需在 M3 之后按其流程单独登记、审阅、实现。
- 大盘状态缺失或过期时，个股项目标注“大盘背景未知”，不默认为正常。

时间预期（2026-10-13）：market-risk 正在走第二道门第四次正式运行；按其线路图，M3 最早约 2–3 周后开始，每日输出模块（market-risk 待办编号 H-7）要等 M3 之后单独登记实现。个股项目第一版应按“没有 market-risk 实时输出”来设计。

## 第二部分：算法与设计建议

先写死产品定义和评价方法，再写代码；算法上按三层拆风险、按波动率定阈值、反弹提醒分阶段并带失效条件。

### 1. 产品定义（开工前达成一致）

- 风险预警指哪几种事件：从高点回撤、跌破均线、相对大盘或板块走弱、波动率放大、跳空大跌、财报前后。每种都是独立、可解释的规则。
- 反弹提醒定义为“下跌后出现止跌确认”，不是“到底了”；系统和 market-risk 一样是跟随确认式。
- 只给方向、不给买卖数量，数量由用户自己定。
- 股票池只含美国本土上市公司，不含中概股、A 股、港股；第一版只做 20–50 只自选观察名单。
- 频率：日线收盘后计算；盘中实时不在第一版。

### 2. 把风险拆成三层

| 层 | 含义 | 数据来源 |
| --- | --- | --- |
| 市场层 | 整个大盘在跌 | market-risk 状态（第一版用简化替代） |
| 板块层 | 所在行业在跌 | 板块 ETF（如 XLK、SMH、XLF）的相对强弱 |
| 个股层 | 公司自身问题 | 相对大盘、相对板块的超额回撤；财报、跳空 |

每条提醒说明是哪一层引起的：市场层下跌看大盘信号，个股层下跌才单独处理这只股票。

### 3. 阈值按个股波动率归一化

- 固定百分比会让高波动股天天报警、低波动股永远不报。回撤阈值改用该股自身波动为单位，例如“回撤超过 k 倍 N 日 ATR 或日收益标准差”。
- 波动率只用信号日之前的数据；大跌期间波动率会抬高、阈值随之变宽，需要明确是否冻结在下跌开始前的水平。
- k、N 的候选网格要小，并在看结果之前登记。

### 4. 风险预警的状态机

- 每只股票一个状态机，状态例如正常 / 关注 / 警戒（名称待定）。
- 升级即时、可跨级；降级一次一档，需连续若干天确认。
- 加冷却期和去重：同一只股票同一状态在一段时间内只提醒一次。
- 每条提醒附触发规则和当时数值，例如：收盘距 63 日高点回撤 14.2%，超过 3 倍 ATR；同期 SPX 回撤 2.1%，大盘状态正常，判定为个股层。

### 5. 反弹提醒：分三阶段、带失效条件

1. 止跌观察：连续若干天不再创 N 日新低（与 market-risk 降级条件同一思路）。
2. 反弹确认：收盘重新站上短期均线，或形成更高的低点。
3. 趋势恢复：站上中期均线，且相对大盘不再走弱。

- 失效条件：跌破止跌观察期的最低点即回到下跌状态，并提醒“反弹失败”。
- 市场过滤：大盘仍在二级时，个股反弹提醒降为“观察”并标注“大盘尚未止跌”。是否真的提高可靠性，要在回测中验证。
- 反弹提醒应少而确认度高，符合“等明确机会、不频繁操作”的原则。

### 6. 个股特有的数据问题

- 复权：拆股、分红会让未复权价格出现假暴跌。回撤和均线用复权价；复权价会随新分红回溯变化，回测要固定数据版本。
- 幸存者偏差：只用现在还在上市的股票回测，会高估反弹成功率。历史股票池按当时构建，或至少明确声明这一偏差。
- 停牌、缺数据、退市：缺数据时不进入也不解除状态，并提醒用户。
- 财报日：作为独立事件输入单独标注，不混在价格规则里。
- 数据源：目前用 Tiger 数据；回测需要的长历史复权数据要确认来源和授权。
- 将来加入基本面数据，必须用当时已公布的值，否则严重前视。

### 7. 评价方法在写代码之前登记

| 对象 | 指标 |
| --- | --- |
| 风险预警 | 提醒后 N 天内最大回撤分布；误报率；漏报率；每只股票每年提醒次数；提醒相对下跌起点的滞后天数 |
| 反弹提醒 | 提醒后 N 天收益的分位数分布；反弹失败率；加与不加市场过滤的对比 |
| 基线 | 固定百分比回撤、均线交叉、随机日期；打不过基线就不值得复杂化 |

- 按时间切分开发期和验证期，验证期只跑一次，结果称“冻结后的历史检验”。
- 参数网格小、事先登记。
- 多重检验：所有股票用统一参数（或按波动率分组），不要每只股票单独挑最优参数。

### 8. 第一版范围（MVP）

- 20–50 只美国本土个股，日线、收盘后计算。
- 风险预警 2–3 条规则 + 一个状态机；反弹提醒 1 条规则（止跌观察 → 反弹确认），带失效条件。
- 市场背景先接简化版（或手工录入），预留 market-risk 每日输出接口。
- 输出：每日一张提醒表 + 推送。
- 技术栈：Python 计算；存储用 MySQL；FastAPI 接口与 Vue3 + Element Plus 前端先做规划、第一版不开发（见第 12 节）。

### 9. 纪律与风控

系统负责计算、提醒和记录，所有风控数字由用户填写；纪律分为代码里的系统纪律和用户的执行纪律两层，都要设计。

**系统纪律（写进代码）**

| 规则 | 做法 | 用户填写 |
| --- | --- | --- |
| 单笔风险预算 | 买入前先定这笔最多亏账户的百分之几，再按止损距离倒推股数；高波动股自动买得少 | 每笔风险占账户 \_\_% |
| 波动率止损 | 跌破买入价 k 倍 ATR 即提醒卖出，不用固定百分比 | k = \_\_ |
| 集中度上限 | 单只股票、单个板块的仓位上限 | 单股 \_\_%，单板块 \_\_% |
| 组合层熔断 | 个股账户从高点回撤到熔断线，暂停新开仓 | 熔断线 \_\_%，恢复条件 \_\_ |
| 不在下跌中摊平 | 股票处于风险预警状态时禁止加仓；到“反弹确认”阶段才允许再买 | — |
| 财报前规则 | 财报前若干天是否减仓或不新开仓 | 提前 \_\_ 天，动作 \_\_ |
| 大盘过滤 | 大盘在二级时，个股新开仓只允许小仓位或不开 | 上限 \_\_% 或不开 |

这些规则本身也要纳入第 7 节的评价：在回测中对比“有无此规则”的最大回撤和收益，不预设它们一定有用。

**执行纪律（用规则和记录约束）**

- 预先承诺：每只股票买入时就写下止损位、风险预警时的动作、反弹确认时的动作；信号来时照表执行。
- 执行记录：每条提醒对应一行记录——系统信号、实际操作、是否一致、不一致的理由。系统提供这张表，不需要用户另记。
- 偏离冷静期：要违背信号操作时，先写下理由，第二天再决定。
- 定期复盘：每季度对照执行记录，统计偏离信号的次数，以及事后看偏离是对是错。

### 10. 边界：大语言模型不进入核心，事件日历只做提示（都不在第一版必做范围）

信号计算不接入大语言模型；宏观事件提醒用结构化日历即可，也不需要模型。两者都是可选的外围功能，第一版可以不做；本节只是写清楚将来要做时的边界。

- 事件日历：FOMC 议息、CPI、非农、个股财报日期都是提前公布的固定日程，建一张表（日期、事件类型、标的、来源），每日输出附“未来 5 个交易日事件”。第一版只提示，不改变状态机；以后若要“事件前收紧阈值”，先登记再回测。
- 大语言模型只做三件事：把系统已算出的信号写成说明文字；整理 Tiger 等来源的消息面，标注“参考，不构成信号”；提取财报和公告要点，结果要能对回原文。
- 每次调用记录输入、输出、模型版本和时间；不能用大语言模型回测“当时它会怎么判断”，因为模型训练时已经见过历史行情。

### 11. 来自 market-risk 的工程与流程经验

这些是 market-risk 在第二道门和两次全流程演练中实际踩过的坑，个股项目从第一天就照做。

- 正式运行期间，仓库目录里不开 IDE、不运行任何其他 AI 工具；审阅类智能体只读仓库外的副本。market-risk 演练 2 就因为运行期间仓库里多出两个外部写入的文件而在最后一步停止。
- 每个正式运行都先做一次全流程演练，演练结果单独登记，不当作证据，也不写成“通过”。
- 执行指令用“脚本文件 + 清单哈希”绑定，一节一次调用，任一不符即停，不重试、不续跑；状态未知只查询原调用。
- 跨平台一致性要实测：Windows Git Bash 与 Linux 的 `sha256sum` 输出格式不同，清单口径必须写死（例如 `sha256sum -b`、`LC_ALL=C` 排序）。
- 云端验证只算开发验证，真实环境以 Windows 实跑为准。
- 执行方回报全文保存，节录另立文件；每次停止都登记“已执行、未执行”的边界。
- 每个阶段请独立审阅方（如 ChatGPT）复核，审阅时先盲审代码，再看流程材料，避免被已有结论带偏。

### 12. 项目结构（按 Spring Boot 式分层）

Python + FastAPI 也能做到 Spring Boot 那样的分层：每层一个目录，依赖只能从上往下，并用工具在测试里强制检查。

```text
├─ config/

│  └─ registered_params.yaml        已登记的算法参数，只读，改动须走登记流程
├─ src/stock_risk/
│  ├─ api/                          接口层（≈ Controller）【规划，第一版不开发】
│  │  ├─ routers/                   alerts.py · watchlist.py · journal.py · events.py

│  ├─ service/                      业务编排层（≈ Service）

│  ├─ domain/                       纯计算核心（≈ Domain），不读文件、不联网、不取当前时间

├─ research/                        回测与评价，只引用 domain，不进生产代码
├─ tests/
│  ├─ unit/                         domain 层测试，期望值手工推导

│  ├─ architecture/                 分层依赖检查
│  └─ fixtures/                     只放构造数据，不放真实行情
├─ db/migrations/                   MySQL 表结构迁移（alembic，≈ Flyway）
├─ frontend/                        Vue3 + Element Plus + ECharts【规划，第一版不开发】
├─ docs/                            设计、登记、裁决
└─ data/                            本地行情，不入 git
```

**分层依赖规则**

| 层 | 可以依赖 | 不得依赖 |
| --- | --- | --- |
| api | service、api/schemas、core | repository、infra、domain 内部实现 |
| service | domain、repository、core | api |
| domain | 只依赖标准库与自身 | 任何其他层、数据库、网络、大语言模型库 |
| repository | infra、domain/models、core | service、api |
| infra | core | domain 的计算逻辑、service、api |
| jobs | service、core | domain、repository（一律经 service） |
| research | domain | service、repository、api |

这张表用 import-linter 写成契约，放在 `tests/architecture/`，违反即测试失败，和 Java 里用 ArchUnit 是同一个思路。

### 13. 代码开发纪律（开工前写入 CLAUDE.md 与 README）

**设计与算法**

1. 先登记后编码：算法参数与候选网格写入 `registered_params.yaml` 并经复核，代码里不出现魔法数字。
2. 无前视：domain 函数一律接收 `as_of` 日期，只用该日及以前的数据；当前时间只通过 `core/clock` 注入。
3. domain 层是确定性纯函数：同样输入永远同样输出，无全局状态、无随机数、无 IO。
4. 数值口径写死：价格精度、浮点容差、复权方式在设计文档中登记。

**编码**

5. 全量类型标注，mypy 严格模式；ruff 统一风格与检查；提交前由 pre-commit 自动运行。
6. 实体用不可变 dataclass；层与层之间只传模型，不传数据库对象。
7. 异常分类处理：禁止裸 `except` 和静默吞错；缺数据、非有限值、长度不符一律明确失败或返回显式状态，不用空值代替。
8. 依赖注入：service 通过构造参数拿到 repository 与 clock，便于测试替换。
9. 密钥只从环境变量读取，永不入库；`data/` 与本地数据库写入 `.gitignore`。

**测试**

10. 期望值从规格手工推导，禁止“改期望值迎合实现”。
11. domain 层每条规则至少有正例、反例、边界例（含缺价、窗口不足、等号边界）。
12. 测试只用构造数据；真实行情只在经批准的正式运行中读取。
13. 关键计算另写独立回算脚本（不 import 项目代码）交叉核对。

**流程**

14. 小步提交，每次提交只做一件事；合并前由另一个智能体独立审阅。
15. 改已登记的规则或参数，必须走“登记 → 复核 → 批准”，不因一次复盘或一段行情临时改动。
16. 大语言模型相关代码只允许出现在 infra 与 service 的说明生成环节，domain 层禁止引用（由分层契约检查）。

### 14. 技术选型与开发顺序

| 部分 | 选型 | 第一版 |
| --- | --- | --- |
| 计算与定时任务 | Python（uv 管理） | 开发：domain、service、repository、infra、jobs |
| 存储 | MySQL（SQLAlchemy + alembic 迁移） | 开发：行情、提醒、执行记录、事件表 |
| 接口 | FastAPI | 只规划：目录与分层规则先定，代码后做 |
| 前端 | Vue3 + Element Plus + ECharts | 只规划：页面为每日提醒表、个股详情（价格、状态、触发原因）、执行记录、观察名单维护 |

库表先按将来接口与前端的需要设计，第一版用命令行与推送查看结果；接口与前端上线时不需要改动 domain 与库表。

### 15. 行情数据来源

程序取数走接口，不走 TradingView。

- **TradingView 不适合作数据来源**：它目前没有面向个人开发者的历史行情接口，官方帮助中心自述“暂无提供数据的 API”；第三方“TradingView 接口”用的是未公开的内部端点，不稳定，很可能违反其服务条款；手工导出 CSV 有条数上限，也无法自动化。[来源](https://blog.traderspost.io/article/tradingview-api)
- **TradingView 可以用在展示上**：它的开源图表库 Lightweight Charts（Apache 2.0）只负责画图、数据由我们自己提供，将来前端画 K 线可以和 ECharts 二选一；你自己看盘继续用 TradingView 网站也不受影响。
- **首选：老虎证券 Tiger Open API**：你已有账户，Python SDK `tigeropen` 提供行情查询，含 K 线周期与复权类型参数。开工前要确认：美股行情权限是否已开通、日线历史能取多长、调用频率限制、复权方式。[文档](https://docs-en.itigerup.com/docs/basic) · [PyPI](https://pypi.org/project/tigeropen/)
- **长历史回测可能需要第二来源**：若 Tiger 的历史深度或复权口径不够，再评估专门的行情数据服务（价格与授权条款开工前再查，本文不预设）。
- **工程做法**：数据源都封装在 `infra/data_sources/` 后面，统一接口，换源不动 domain；入库保存未复权原始价格、复权因子、来源与取数时间，回测按数据版本固定；每日取数后做缺失、重复、异常跳变核对。
- market-risk 的 SPX、QQQ 也可以走同一个数据源封装，但两个项目各自入库、各自绑定数据版本。
